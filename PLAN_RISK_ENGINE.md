### 1.1. Роль JSON-файлів — відповідь на питання

`tools/antifrod_concepts.json`, `antifrod_reviews.json`, `antifrod_trade_terms.json`
**в рантаймі не читаються жодного разу.** Єдиний споживач — генератор
`tools/build_rules.py`, який з них будує `rules.py`.

Але й генератор зараз нічого не оновлює:

```python
# tools/build_rules.py:38
OUT_RULES = SOURCE_DIR / "core" / "rules.py"     # SOURCE_DIR = tools/
```

Тобто він пише в `tools/core/rules.py`, а такої теки **не існує** —
`write_text` на неї впаде. Бойовий файл лежить в іншому місці:
`core/analysis/rules.py`. Його одного разу скопіювали руками (шапка досі
каже `# core/rules_generated.py`, а інструкція всередині — «скопіюйте нові
RegexRule в production rules.py»), і з 25.07 він заморожений.

Підсумок: **JSON-и — це не конфіг, а вихідний матеріал зламаного генератора.**
Викидати їх не треба — навпаки, їхня схема це майже готова модель правила
для нового конфігуратора:

```json
{"phrase": "писати до оплати", "category": "CHAT_FIRST", "severity": "SOFT",
 "ambiguous": true, "suppress_hard": [], "variants": ["пишіть до оплати", "…"],
 "why_risky": "Класичний прийом виведення угоди з чату біржі…",
 "example_positive": "…", "example_negative": "…",
 "regex_hint": "пишіть?.{0,15}(до оплат|перед|спочатку)|…", "confidence": 0.72}
```

Тут уже є все, чого бракує теперішньому `RegexRule`: варіанти фраз (не
регекс), пояснення «чому це ризик», приклади в обидва боки, впевненість.
Саме цим і треба засівати нову таблицю правил (Етап 3).

### 2.1. AI-вижимка відгуків нікуди не доїжджає

`core/workers/llm_worker.py:943` — `_parse_json` повертає словник із п'яти

```python
return {"status", "risk", "reason", "trade_recommendation", "terms_summary"}
```

```python

```

Далі порожній рядок їде через `save_verdict` у БД, звідти в
`get_trade_recommendation_full`, звідти в `alert_builder.py:104`, звідти в
`formatters.py:238`, де блок просто не малюється.

Тобто: системний промпт вимагає `reviews_analysis` трьома окремими
абзацами (`llm_worker.py:124, 149–155`), модель його чесно генерує, ми його

Перевірка по базі:

```

  з непорожнім terms_summary    — 1137
  з непорожнім reviews_analysis —   14
```

Ті 14 — не від моделі. Це захардкожені рядки з `risk_engine.py:998` і `:1073`
(«Відгуки чисті, без скарг на шахрайство.», «Загроз не виявлено.»).

### 2.2. Правила для відгуків працюють по умовах угоди

`core/analysis/rules.py` має прапорець `review_only` — правила, які можна
застосовувати **тільки до текстів відгуків**, бо вони написані під чужу мову
(«кинув», «шахрай», «дроп») і мають вагу 100.

`review_fetcher.py:50` цей прапорець поважає:

```python
_REVIEW_ONLY_RULES = [r for r in ALL_RULES if getattr(r, "review_only", False)]
```

А `regex_analyzer.analyze()` — ні:

```python
# core/analysis/regex_analyzer.py:261
for rule in SOFT_RULES:          # ← фільтра по review_only немає
```

З 25 правил у `SOFT_RULES` **18 мають `review_only=True`**, з них 7 з вагою
100 і 7 з вагою 50. Поріг ескалації — `LLM_SCORE_THRESHOLD = 30`. Тобто
одне випадкове спрацювання review-правила на умовах мерчанта дає score 100,
`verdict=NEEDS_LLM`, `risk_type=TRIANGLE` — і LLM отримує промпт, у якому
вже написано «Regex main risk: TRIANGLE».

Розподіл у базі узгоджується з цим: `TRIANGLE 457`, `FINCRIME 247` —
разом 55% усіх вердиктів, при 892 BLOCK з 1290 (69%).

Ще один бік тієї самої дірки: у `SAFE_RULES` теж є `review_only=True`
правило (`GEN_F03_SAFE`, вага −50), і воно так само глушить умови.

### 2.3. Ріск-енджин досі пише службовий текст у поле умов

`core/engine/terms_status.py` існує саме для того, щоб цього більше не було
(докстрінг файла це прямо описує). Wallet і CryptoBot виправлені, тест
`tests/test_terms_status.py:138` це стереже. Але шість місць у самому
ріск-енджині роблять рівно те, від чого відмовились:

```python
# core/engine/risk_engine.py:462, 491, 495, 502, 515, 519
order.trade_terms = "не вдалося отримати доступ до умов через відсутність активної сесії"
```

Наслідки, по порядку руху цього рядка:

1. `regex_analyze(terms, …)` аналізує його як текст мерчанта;
2. він їде в LLM усередині `<merchant_terms>` (`llm_worker.py:720`) — модель
   читає нашу службову помилку як умови угоди й переказує її в `terms_summary`;
3. `hash_terms(terms)` від нього однаковий для **всіх** мерчантів без сесії —
   а це ключ кешу вердикту (`merchant_repo.py:246`) і поле `terms_hash` у
   снапшотах (`merchant_repo.py:599`), на якому тримається `FLICKER_RELIST`
   (`behavioral_analyzer.py:151`);
4. `order.terms_status` при цьому лишається незайманим — тобто єдине поле,
   яке мало б сказати правду, мовчить.

Це і є те, про що йшлося: запобіжник зробили, ріск-енджин про нього не знає.

### 2.4. `MerchantFilter.passed()` падає в STRICT

```python
# filters/merchant_filter.py:49
def passed(self, order: Order) -> bool:
    if order.merchant_name in self.blocked_names:
        return False
    if self.risk_mode == "WARNING":
        return True
    if not risk_flag or risk_flag in SAFE_FLAGS:     # ← risk_flag не існує
```

Локальної змінної `risk_flag` у методі немає, `order.risk_flag` ніхто не
читає. Дефолт `WARNING` виходить рядком вище, тому в проді не стріляє. Але
`settings.risk_mode` читається з `.env` (`config/settings.py:72`), і
`RISK_MODE=STRICT` кладе `NameError` на кожен ордер у циклі сканера.

Додатково: `scanner.py:306` створює фільтр **один раз на старті** з
`settings`, а не з `runtime_config`. Тобто пункт меню «🛡 Рівень антифроду»
(`bot/handlers/core.py:337`, `bot/handlers/exchanges.py:432`) не впливає ні
на що — класика з `silent-failure-patterns`.

### 2.5. `API_ERROR` читається як «відгуки чисті»

`_build_review_flags_from_summary` (`risk_engine.py:172`) знає п'ять
«сліпих» статусів:

```python
if status in ("UNAVAILABLE", "NOT_SUPPORTED", "NO_AUTH", "UNKNOWN", "NO_SESSION"):
    return [f"UNKNOWN:REVIEWS:{status}"]
```

`review_fetcher.py:385` уміє видавати ще один — `API_ERROR` (біржа відповіла
помилкою). Його в списку немає, тож він провалюється нижче, де `pos=neg=0`,
`total=0`, і функція повертає `[]` — тобто «претензій немає». Та сама
історія, що з `NO_SESSION` до її виправлення, тільки з іншим статусом.

Симетрично: `terms_status.SESSION_EXPIRED` є в `BLIND`
(`terms_status.py:32`), але в списку відгуків його теж немає.

### 2.6. `trusted_skip` вигадує стан відгуків

```python
# core/engine/risk_engine.py:991
await self._db.save_verdict(..., "OK", "NONE",
    f"Довірений мерчант ({order.month_order_count} угод, …). Ризиків не виявлено.",
    "trusted_skip", trade_recommendation="APPROVE",
    terms_summary="Умови обміну перевірено, стандартні вимоги безпеки.",
    reviews_analysis="Відгуки чисті, без скарг на шахрайство.")
```

Гілка спрацьовує, коли `has_review_concern` порожній. Але `has_review_concern`
шукає `"BADREVIEWS" in f` — а прапор «відгуків не бачили»
(`UNKNOWN:REVIEWS:NO_SESSION`) цього підрядка не містить. Тобто мерчант,
чиїх відгуків ми не завантажили жодного, отримує в базу текст «відгуки
чисті, без скарг на шахрайство» і `APPROVE`. І далі цей текст показується
в алерті як AI-вижимка.

Те саме, м'якше, у `risk_engine.py:1066`: `terms_summary="Умови стандартні."`
для мерчанта, чиї умови ми не бачили (сюди він потрапляє рідше, бо
`UNKNOWN:TERMS` тримає `risk_flag != "OK"`, але гілка на це не спирається —
вона спирається на побічний ефект).

### 2.8. «Відгуків не видно» не показується людині взагалі

Це найгірший із усіх, бо саме він тримає скаргу з постановки задачі.

Ріск-енджин чесно ставить `UNKNOWN:REVIEWS:NO_SESSION`. Далі є два
рендери прапорів, і вони поводяться по-різному:

| Функція | Що робить з `UNKNOWN:` | Хто викликає |
|---|---|---|
| `formatters.format_risk_line` (`:130`) | малює «❔ НЕ ПЕРЕВІРЕНО: відгуки — немає сесії біржі» | **ніхто** (тільки тести) |
| `formatters._risk_badge` (`:374`) | **мовчки ігнорує** | `alert_builder:222,223,673`, `taker_builder:333`, `maker_builder:124` |

Перевірка на живій функції:

```
'UNKNOWN:REVIEWS:NO_SESSION'                   -> ''
'UNKNOWN:TERMS:NO_SESSION'                     -> ''
'UNKNOWN:REVIEWS:API_ERROR,BLOCK:TRIANGLE:щось' -> '🚫 ТРИКУТНИК / ДРОП'
'LOW_STATS,UNKNOWN:TERMS:EMPTY'                -> '⚠️ МАЛО УГОД / НИЗЬКИЙ %'
```

У циклі `_risk_badge` немає гілки `startswith("UNKNOWN:")`, а фолбек
`if f in badges` не спрацьовує, бо `UNKNOWN:REVIEWS:NO_SESSION` — не ключ
словника.

Про **умови** людина все-таки дізнається: `_terms_block` (`formatters:245`)
малює «Умов не видно — немає сесії біржі» з окремого поля
`order.terms_status`. Про **відгуки** — не дізнається нізвідки. При цьому
текст вердикту від моделі (`reason`) показується і цілком може стверджувати,
що з відгуками все гаразд.

Тобто робота «UNKNOWN замість тихого OK» доїхала до движка й до умов, але
не доїхала до відгуків у рендері.

### 2.10. `"BLOCK" in risk_flags` ловить `..._BLOCKED`

Підрядок `BLOCK` міститься в слові `BLOCKED`:

```
'FOP_TOV_BLOCKED'   -> "BLOCK" in it: True
'BANKA_JAR_BLOCKED' -> "BLOCK" in it: True
```

Чотири місця роблять саме таку перевірку:

* `core/engine/alert_dispatcher.py:284` — `elif "BLOCK" in risk_flags`
* `bot/handlers/monitoring.py:369,371` — і це **до** перевірки фільтра
* `bot/handlers/monitoring.py:455`
* `core/engine/taker_scanner.py:555`

Наслідок: ордер із ФОП/ТОВ або банкою відкидається **завжди**, незалежно
від того, що людина вибрала. Режими «⚠️ попереджати» і «показувати» в
налаштуваннях недосяжні — гілка `filter_fop == "hide"` вище просто дає
іншу причину в лозі, а результат один.

Разом із дірками регексу з розділу 3 це дає рівно ту картину, яку описав
користувач: коли прапор не поставлено — ордер приходить попри «не
присилати»; коли поставлено — зникає навіть у режимі «попереджати».

### 2.11. Невдалий фетч відгуків стирає вже відомі відгуки

`fetch_now` на будь-якій помилці і на відсутності сесії пише в базу нулі:

```python
# core/workers/review_fetcher.py:388 (except) і :281 (NO_SESSION)
await self._db.save_reviews(exchange, merchant_id, 0, 0, 0, [], status=status, …)
```

`save_reviews` (`merchant_repo.py:494`) — upsert, який перезаписує **всі**
колонки: `positive_count`, `negative_count`, `neutral_count`,
`bad_texts_json`. Тобто мерчант, чиї 500 відгуків і тексти скарг ми успішно
зібрали вчора, після однієї невдалої спроби сьогодні лишається з нулями.

Ми не просто не дізнались нового — ми знищили те, що знали. Стан бази:

| status | рядків | з нульовими лічильниками | без текстів |
|---|---:|---:|---:|
| NO_SESSION | 2257 | 2257 | 2257 |
| OK | 1822 | 822 | 997 |
| UNAVAILABLE | 358 | 358 | 358 |
| NO_FEEDBACK | 113 | 113 | 113 |
| NOT_SUPPORTED | 73 | 73 | 73 |
| API_ERROR | 51 | 51 | 51 |
| PENDING | 1 | 1 | 1 |
| **разом** | **4675** | | |

Реально придатних даних — близько 1000 рядків із 4675 (21%). Решта — або
не зібрані, або затерті.

Правильна поведінка: при технічній невдачі міняти **тільки** `status`,
`error_reason` і `updated_at`, лишаючи останні відомі лічильники й тексти
на місці. Тоді вердикт зможе сказати «останні відомі відгуки від 12.08,
свіжіших дістати не вдалось» — а це і є чесна відповідь.

### 2.12. `needs_review_fetch` довбає біржу без бекофу

```python
# core/storage/merchant_repo.py:478
if status in ("PENDING", "UNAVAILABLE", "API_ERROR", "SESSION_EXPIRED", "NO_FEEDBACK"):
    return True
```

Без урахування `updated_at`. Тобто мерчант, у якого відгуків справді нема
(`NO_FEEDBACK`), перезапитується **кожен цикл назавжди**. Так само
`API_ERROR` і `UNAVAILABLE` — без затримки й без зростання інтервалу.
Частково рятує degraded-mode cooldown у `fetch_now:226`, але він вмикається
лише після трьох відмов поспіль і діє на всю біржу цілком.

`NO_FEEDBACK` тут узагалі не на місці: це успішна відповідь, а не збій.

### 2.13. Половина глобальних налаштувань ризику ні на що не впливає

`config/runtime.ALLOWED_KEYS` пускає в UI сім ризикових ключів. Насправді
працюють тільки ваги:

| Ключ | Пункт меню | Хто читає в рантаймі |
|---|---|---|
| `W_REGEX` … `W_IDENTITY` | ✅ | ✅ `CompositeScorer.load_weights`, викликається зі `scanner.py:236,509,551` |
| `review_ttl_hours` | ✅ | ⚠️ тільки на старті: `scanner.py:257` → конструктор `ReviewFetcher` |
| `behavior_alert_score` | ✅ | ❌ ніхто |
| `velocity_spike_per_hour` | ✅ | ❌ ніхто |
| `sticky_min_chain` | ✅ | ❌ ніхто |
| `risk_mode` | ✅ | ❌ ніхто (див. 2.4) |
| `block_fop_tov` | ❌ | ❌ ніхто |
| `block_banka_jar` | ❌ | ❌ ніхто |

Причина для трьох середніх однакова: `behavioral_analyzer.py:6` тягне
`VELOCITY_SPIKE_PER_HOUR`, `STICKY_MIN_CHAIN` з `config/defaults` **на
рівні модуля**, тож значення фіксується при імпорті й переживає будь-яку

Окремо: `risk_engine.py:42` заводить власну `BEHAVIOR_ALERT_SCORE = 60`,
не імпортуючи її з `config/defaults.py:8`. Тобто константа існує у двох
екземплярах, і той, що в дефолтах, мертвий.

Це прямо стосується задачі: конфігуратор із Етапу 4 має читатись **у
момент рішення**, а не при імпорті модуля, інакше він повторить цю ж долю.

### 2.14. Спільний `Order` мутується під кожного користувача

`alert_dispatcher.py:548` робить `local_alert = copy.copy(alert)` — копія
**поверхнева**. `local_alert.buy_order` і `sell_order` — ті самі об'єкти для
всіх користувачів у батчі.

А `alert_builder.send_single` їх мутує: `order.risk_flag` (`:191`),
`order.review_neg_pct` (`:140`), `order.review_fetched` (`:143`) — причому
`risk_flag` переписується під **персональні** налаштування показу
(`filter_fop_tov` / `filter_banka_jar`, `:173–189`).

Тобто другий користувач у циклі бачить прапор, похідний від налаштувань
першого. Поки фільтрів два і вони обидва зводяться до «сховати» (2.10), це
майже не помітно — але Етап 5 робить персональну політику головним
механізмом, і тоді це поламає все. Лікується `copy.deepcopy` на ноги або,
краще, тим, що рендер узагалі перестає мутувати вхідний об'єкт.

### 2.15. На сайті вижимка відгуків не має захисту від сліпоти

`api/verdict_refresh.py:84` має `_drop_blind_terms` — прибирає вижимку
**умов**, зроблену наосліп. Симетричної перевірки для `reviewsAnalysis`
немає, хоча поле віддається (`:80`).

Зараз не стріляє лише тому, що `reviews_analysis` завжди порожній (2.1).
Щойно 2.1 полагодять — сайт почне показувати аналіз відгуків, зроблений
без відгуків. Тобто це не «ще один баг», а **обов'язковий супутник фікса
2.1**, і робити їх треба одним заходом.

Там же дрібниця: докстрінг `_drop_blind_terms` каже «вердикт живе в кеші до
12 годин», а насправді `VERDICT_MAX_AGE_DAYS = 3` (`risk_engine.py:46`).

### 2.16. Промпт наказує моделі стверджувати чистоту за вигаданими числами

`risk_engine.py:571–595` для Binance/Bybit підставляє `positive` з
`month_order_count`, коли профіль віддав нуль:

```python
pos_est = max(0, total_est - neg_est)      # total_est = month_order_count
review_summary_raw["estimated_from_stats"] = True
```

Кількість **угод** видається за кількість **відгуків**. Далі
`llm_worker.py:798` бачить `neg == 0` і дописує в промпт:

> ⬆️ ВІДГУКИ ПОВНІСТЮ ЧИСТІ: Жодного негативного відгуку! Мейкер має
> бездоганну репутацію. Обов'язково вкажи у thought_process, reason та
> reviews_analysis: «відгуки чисті, негативні відгуки відсутні, репутація
> чиста».

Позначка `(оцінено зі статистики профілю)` поруч є, але вона слабша за
пряму директиву. Модель отримує наказ написати «репутація чиста» про
мерчанта, чиїх відгуків ніхто не бачив.

Це той самий принцип, що й у [[no-invented-metrics]], тільки всередині
движка: оцінка подається як факт. Або рахуємо чесно й називаємо оцінкою в
самому вердикті, або не рахуємо взагалі.

### 2.17. VACUUM не виконався жодного разу ✅ виправлено 11.08.2026

Не з ризик-движка, але з тієї самої родини: команда є, лог про неї є,
роботи немає. В `logs/error.log` один і той самий рядок від червня 2026:

```
2026-06-07 | ERROR | DBMaintenance | Помилка виконання SQL у DB Maintenance: cannot VACUUM - SQL statements in progress
2026-07-01 | ERROR | …
2026-07-25 | ERROR | …
2026-08-05 | ERROR | …
```

Помилку ловив загальний `except`, тому обслуговування вважалось робочим:
чистка перед VACUUM відпрацьовувала й комічувалась (це видно в базі —
`merchant_review_history` рівно за 30 днів, снапшоти за добу), а стиснення
не відбувалось ніколи.

Спокуслива гіпотеза «хтось тримає курсор через конкурентність» — хибна.
Причина статична й наявна з моменту старту процесу. SQLite забороняє VACUUM,
доки на з'єднанні лишається незавершений statement, а незавершеним рахується
будь-який, що **повертає рядки** і чий курсор не вичерпали. У
`MerchantDB.start()` таких два:

```python
await self._db.execute("PRAGMA journal_mode=WAL")     # повертає 'wal'
await self._db.execute("PRAGMA busy_timeout=10000")   # повертає 10000
```

Заміряно окремим пробником на порожній базі:

| Перед VACUUM | Результат |
|---|---|
| нічого | OK |
| `PRAGMA synchronous=NORMAL` (рядка не повертає) | OK |
| `PRAGMA foreign_keys=ON` (рядка не повертає) | OK |
| `PRAGMA cache_size=-65536` | OK |
| `PRAGMA busy_timeout=10000` | **FAIL** |
| `PRAGMA journal_mode=WAL` | **FAIL** |
| `SELECT 1` | **FAIL** |

**Зроблено:**
* `MerchantDB.start()` вичерпує кожен PRAGMA через `async with … fetchall()`
  — витік statement-ів на спільному з'єднанні усунено в корені;
* VACUUM переїхав у `DBMaintenanceTask._vacuum()` на **окреме** з'єднання з
  `isolation_level=None`, з `wal_checkpoint(TRUNCATE)` перед стисненням і
  звітом «було → стало» в лозі;
* невдале стиснення більше не мовчить у загальному `except`, а логується
  окремим рядком;
* `tests/test_db_maintenance.py` — 5 тестів, зокрема на живому з'єднанні
  застосунку і з навмисно відкритим чужим курсором.

Стан бази на момент фікса: 15.1 MB, freelist 0.2%, тобто самого місця
VACUUM звільнив би небагато. Цінність фікса не в мегабайтах, а в тому, що
щодобова помилка більше не маскує реальні проблеми обслуговування.

## 3. Чому вижимка перекручує умови

Приклад користувача: в умовах написано «кидаю на **монобанку** і **конверт
приват**», модель переказала це як «мерчант кидає на монобанк і приватбанк».

Це не галюцинація, це брак словника. «Монобанка», «банка», «конверт»,
«збір», «скарбничка» — це **накопичувальні рахунки**, окремий продукт із
іншим режимом фінмону, а не назви банків. Модель не має звідки це знати:
у системному промпті (`llm_worker.py:82–155`) немає жодного слова про
українську банківську специфіку.

Регекс це частково знає, але дірявo. Прогін `check_custom_blocks_metadata`
(`regex_analyzer.py:98`) на реальних формулюваннях:

| Текст умов | Результат |
|---|---|
| `кидаю на монобанку і конверт приват` | ✅ `BANKA_JAR_BLOCKED` |
| `оплата на банку моно` | ✅ `BANKA_JAR_BLOCKED` |
| `скидаю на банку` | ✅ `BANKA_JAR_BLOCKED` |
| `кидати на копилку` | ✅ `BANKA_JAR_BLOCKED` |
| `send.monobank.ua/jar/xxx` | ✅ `BANKA_JAR_BLOCKED` |
| `приймаю на монобанку` | ❌ пропущено |
| `а-банк збір, приват конверт` | ❌ пропущено |
| `накопичувальний збір абанк` | ❌ пропущено |
| `оплата на скарбничку` | ❌ пропущено |

`BANKA_JAR_PATTERN` (`regex_analyzer.py:47`) вимагає `\bбань?к[ауи]\b` як
окреме слово або `моно` + пробіл + `банку`. Злите «монобанку» не ловиться —
а це найчастіше написання. Слова `збір` і `скарбничка` в патерні немає
взагалі.

Ось звідки «параметр стоїть не присилати, а воно все одно приходить»: до
`alert_builder.py:173`, який застосовує `filter_banka_jar`, прапор просто не
доїжджає — його ніхто не поставив.

**Висновок:** проблема не в моделі й не в одному регексі, а в тому, що
предметний словник ніде не описаний і не редагується. Він має стати даними
(Етап 3) і потрапляти і в матчер, і в промпт (Етап 6).

## 4. Цільова архітектура

### 4.1. Головний поділ: факти глобальні, політика персональна

`merchant_verdict` — таблиця на `(exchange, merchant_id)`, спільна для всіх
користувачів. Це правильно для фактів («в умовах є фраза X», «5 негативних
відгуків із 200», «ліміти min=max») і **неправильно** для рішень («це
блокувати»), бо рішення в різних людей різні — власне те, з чого почалась
задача.

Отже:

* **Findings (факти)** рахуються один раз, кешуються глобально;
* **Policy (рішення)** застосовується на кожного користувача в момент
  побудови алерта.

Прецедент уже є і працює: FOP/ТОВ і банка вирішуються саме так, персонально,
в `alert_builder.py:173–191`. Новий движок — це узагальнення цієї схеми на
всі сигнали замість двох захардкожених.

### 4.2. Модель сигналу

```python
@dataclass(frozen=True, slots=True)
class Signal:
    key:        str            # "banka_jar", "triangle_third_party"
    category:   str            # "PAYMENT_TARGET" | "THIRD_PARTY" | "OFF_PLATFORM" | …
    title:      str            # "Банка / накопичувальний рахунок"
    why:        str            # чому це ризик — показується людині в алерті
    phrases:    tuple[str,...] # варіанти фраз (не регекс!)
    regex:      str            # опційно, для складних випадків
    negations:  tuple[str,...] # "без банок", "тільки на картку"
    scope:      str            # "terms" | "reviews" | "both"   ← лікує 2.2
    layer:      str            # "hard" | "soft" | "warn" | "safe"
    weight:     int
    suppresses: tuple[str,...] # ключі сигналів, які цей глушить
    owner:      str            # "builtin" | f"user:{id}"
    confidence: float
```

`phrases` — головне поле. Користувач у боті пише фрази людською мовою,
компіляція в регекс (з урахуванням омографів і `\b`) — робота движка, а не
людини. `regex` лишається лазівкою для складних правил.

### 4.3. Політика

```python
@dataclass(frozen=True, slots=True)
class SignalPolicy:
    signal_key: str
    enabled:    bool = True
    on_buy:     str  = "warn"    # "block" | "warn" | "note" | "ignore"
    on_sell:    str  = "block"
    weight_override: int | None = None
```

Роздільні `on_buy` / `on_sell` — це прямо кейс користувача: трикутник у
ролі покупця це одне, у ролі продавця — зовсім інше. Поле `Order.side` уже
існує (`exchanges/base.py:53`), доробляти модель не треба.

Дефолти політики беруться з `layer` сигналу, далі перекриваються профілем
користувача, далі — точковим налаштуванням конкретного сигналу.

### 4.4. Результат замість рядка

```python
@dataclass(slots=True)
class Finding:
    signal_key: str
    source:     str    # "terms" | "review" | "behavior" | "identity" | "llm"
    excerpt:    str    # ЩО саме побачили — цитата
    weight:     int

@dataclass(slots=True)
class RiskReport:
    findings:  list[Finding]
    coverage:  RiskCoverage        # див. 4.5
    composite: int
    llm:       LLMVerdict | None
```

`order.risk_flag` лишається як серіалізований вигляд для сумісності — усі
теперішні споживачі (`formatters`, `alert_dispatcher`, `monitoring`, API)
продовжують працювати, поки їх не переведуть на `RiskReport` поетапно.

### 4.5. Покриття — окреме поле, а не відсутність прапора

```python
@dataclass(frozen=True, slots=True)
class RiskCoverage:
    terms:    str   # terms_status.*  — OK/EMPTY/NO_SESSION/…
    reviews:  str   # OK/NO_FEEDBACK/NO_SESSION/API_ERROR/NOT_SUPPORTED/…
    behavior: bool  # чи вистачило снапшотів (MIN_SNAPSHOTS=3)
    identity: bool  # чи шукали двійників

    @property
    def is_partial(self) -> bool: ...
    def blind_labels(self) -> list[str]: ...
```

Правило, яке має стати незламним і покритим тестом:

> Жоден текст вердикту не має права стверджувати щось про відгуки чи умови,
> яких не бачив. «Не змогли перевірити» і «перевірили, чисто» — різні стани,
> і в алерті вони мають виглядати по-різному.

Це закриває 2.5, 2.6 і корінь скарги «пише що відгуків немає, хоч просто
сесії не було».

## 5. Етапи

### Етап 0 — зупинити кровотечу

Усі баги розділу 2, без зміни архітектури. Групами, бо частину треба
робити одним заходом:

**0.a — чесність про відгуки** ✅ зроблено 11.08.2026

Порядок був саме такий, бо показувати нема сенсу, поки дані затираються:

1. **2.11** — `mark_reviews_unavailable()` замість `save_reviews(0,0,0,[])`
   на всіх шляхах відмови (`review_fetcher`: офлайн, degraded mode,
   NOT_SUPPORTED, NO_AUTH, NO_SESSION, виняток). Міняються лише `status`,
   `error_reason`, `updated_at`. Нова колонка `merchant_reviews.data_at`
   фіксує момент **успішного** збору окремо від `updated_at`, на якому
   тримається бекоф. Разовий backfill проставив `data_at = updated_at` для
   1822 рядків зі `status='OK'` — без нього перший же збій сесії подав би
   їхні реальні відгуки як невідомі.
2. **Третій стан.** `_last_known()` у фетчері віддає останні відомі відгуки
   разом із чесним статусом. З'явилось розрізнення, якого раніше не було:
   *немає даних зовсім* → `UNKNOWN:REVIEWS:*`, *дані є, але вчорашні* →
   `STALE_REVIEWS:{status}:{вік}h` і **звичайна оцінка по них**. Мерчант зі
   вчорашньою скаргою на скам не перестає бути небезпечним через те, що
   сьогодні впала сесія.
3. **2.5** — `REVIEWS_BLIND_STATUSES` тепер включає `API_ERROR`,

4. **2.8** — гілки `UNKNOWN:` і `STALE_REVIEWS:` у **живому** рендері

### Етап 4 — конфігуратор у боті

Новий розділ «🛡 Ріск-енджин» у налаштуваннях (`bot/keyboards/risk.py`,
`bot/handlers/risk.py`):

```
🛡 Ріск-енджин
├ 🎚 Профіль: Збалансований            → пресети + «Свій»
├ 📂 Сигнали за категоріями
│   ├ 💳 Куди йде платіж    (банка, конверт, збір, ФОП/ТОВ, IBAN)
│   ├ 👥 Треті особи        (трикутник, дроп, посередник)
```

Ваги в `CompositeScorer` уже вміють вантажитись з БД
(`risk_engine.py:77 load_weights`, таблиця `bot_settings`, `user_id=0`) —
але глобально. У розділі «Пороги і ваги» це стає персональним.

### Етап 6 — LLM v3

1. **Глосарій** у системний промпт: банка/конверт/збір/скарбничка =
   накопичувальний рахунок, не банк; монобанка ≠ Монобанк; «збір» в А-банку
   це продукт, а не комісія. Ведеться як дані з реєстру (Етап 1), а не
   як текст у коді.
2. **Докази обов'язкові**: кожне твердження в `terms_summary` і
   `reviews_analysis` супроводжується цитатою з вхідних даних. Немає цитати —
   немає твердження.
3. **Покриття в промпті**: замість теперішніх дев'яти гілок `if rev_status ==`
   (`llm_worker.py:732–809`) — один блок із `RiskCoverage`, і жорстка заборона
   говорити про непокрите.
4. **Структурований вихід**: `terms_summary` не рядок, а список пунктів
   `{topic, quote, meaning}` — це і є ліки від «вижимка упускає деталі»:
   модель не може згорнути п'ять вимог в одне речення, якщо формат вимагає
   перелік.
5. `thought_process` зберігати в БД (нова колонка), під тумблером
   `show_ai_logic`.
6. Персональні сигнали користувача передавати в промпт як «на що звертати
   особливу увагу» — інакше конфігуратор впливатиме лише на регекс, а
   AI-вердикт житиме своїм життям.

### Етап 7 — двійники на інших біржах

Теперішній `analyze_identity` (`core/analysis/identity_analyzer.py:33`)
вимагає збігу **трьох** умов: ліміти ±2%, ціна ±0.5%, і `terms_hash`.
Останній не збігається ніколи, бо порівнюються хеші з двох різних функцій
(див. 2.7). Тобто `is_twin` практично завжди `False`, а `W_IDENTITY = 0.10`
у `CompositeScorer` не робить нічого.

Що робити:

* привести хешування до однієї функції (`hash_terms` з `base_db.py:54`);
* перейти від «І» до зваженого збігу: ліміти + ціна вже дають підозру,
  умови її підтверджують — а не блокують висновок своєю відсутністю;
* врахувати покриття: якщо умов не видно на жодній із бірж, це не «не
  двійник», це «не перевірили».

Тільки після цього має сенс «deep research» — розширення пошуку за межі
`find_digital_twins(minutes=15)` (`core/storage/user_repo.py:758`).
