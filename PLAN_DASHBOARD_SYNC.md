# Перенесення ріск-енджину на дашборд

Складено 11.08.2026, після закриття етапів 0–6, 8 і BYOK (див.
`PLAN_RISK_ENGINE.md`). Це вхідна точка для наступної сесії: тут те, що вже
є на беку, чого ще немає на фронті, і які пастки в цьому конкретному
перенесенні.

## 0. Де що лежить

| | |
|---|---|
| Бек (цей репозиторій) | `C:\p2p_scanner`, гілка `feature/risk-engine-rework` |
| Фронт | `C:\arbix-quantum-p2p-scanner` — **окремий репозиторій**, React + Vite + TS |
| Місце стику | `api/routers/control.py`, `api/routers/dashboard.py`, `api/verdict_refresh.py` |
| Клієнт на фронті | `src/services/api.ts`, типи в `src/types.ts` |

**Головне правило цього перенесення** (воно ж — урок із семи місць, де сайт
уже розходився з ботом): **сайт не рахує нічого сам**. Якщо на екрані має
з'явитись рішення, воно приходить з того самого коду, який кличе бот. Друга
реалізація «майже такої самої» логіки в TypeScript розійдеться з першою
протягом місяця — так уже було з фільтрами банків, вижимкою відгуків і
станом умов.

## 1. Що зламано просто зараз

### 1.1. `riskMode` — контрол, який нічого не робить

`src/components/SettingsPanel.tsx:248` — селект «Рівень антифроду»,
`src/components/CommandPalette.tsx:38` — швидка дія «Посилити/послабити
антифрод». Обидва шлють `riskMode`.

Бек цей ключ **відхиляє**: клас, який його читав (`MerchantFilter`),
видалено на етапі 0.e — він спрацьовував ДО аналізу ризику й у дефолтному
режимі пропускав усе, тобто не робив нічого й до видалення. Поведінка
сервера зафіксована тестом
(`tests/test_api_dashboard_contract.py::test_removed_keys_are_rejected_like_any_other_unknown`):

* сам по собі — `400`, у `detail` буде `risk_mode`;
* разом з іншими ключами — решта застосовується, `riskMode` потрапляє в
  `rejected`.

**Що робити:** прибрати обидва місця. На їхнє місце йде профіль ріск-енджину
(розділ 2.1) — він персональний, а не глобальний, і це не перейменування, а
інша сутність.

### 1.2. Легасі-фільтри ФОП/банка ще приймаються через API

`POST /user/display` досі валідує `filterFopTov` / `filterBankaJar`
(`api/routers/control.py:631`). У боті ці два тумблери **прибрані з меню**
й перенесені в ріск-енджин: `RiskRepo.migrate_legacy_filters` одноразово
переносить старий вибір у політику для `PAY_BUSINESS` / `PAY_JAR`.

Міграція не чіпає сигнали, для яких політика вже є. Але якщо фронт запише
старе значення ПІСЛЯ міграції, воно просто ляже в колонку й нікуди не
поїде — людина змінить налаштування, і не станеться нічого.

**Що робити:** прибрати ці поля з UI дашборда одночасно з появою екрана
політики. Поля в API поки лишити — вони потрібні для міграції старих
користувачів.

## 2. Чого на фронті немає взагалі

Порядок — за користю, не за складністю.

### 2.1. Ріск-енджин: профіль, політика по категоріях, власні сигнали

Найбільший блок. У боті це `🛡 Ріск-енджин` (`bot/handlers/risk.py`,
`bot/keyboards/risk.py`), на сайті — нічого.

**API немає жодного.** Треба писати ендпоїнти; уся логіка вже є в
`core/storage/risk_repo.py`, віддавати треба саме її, без другої копії
правил на фронті:

| Потрібний ендпоїнт | Що кличе | Примітка |
|---|---|---|
| `GET /user/risk/profile` | `get_risk_profile` | 4 профілі, `core/risk/policy.PROFILES` |
| `POST /user/risk/profile` | `set_risk_profile` | валідація вже всередині |
| `GET /user/risk/policies` | `get_policies` + `builtin_registry()` | віддавати ефективну дію, не лише override |
| `POST /user/risk/policy` | `set_policy` | `{signalKey, onBuy, onSell}` |
| `DELETE /user/risk/policy/{key}` | `reset_policy` | повернення до дефолту профілю |
| `GET/POST/DELETE /user/risk/signals` | `get_user_signals`, `save_user_signal`, `delete_user_signal` | перевірки всередині `save_user_signal` — не дублювати їх у TS |
| `POST /user/risk/test` | `core.risk.matcher.match_text` | тест-стенд «перевірити текст» |

**Асиметрія купівлі й продажу — не деталь UI, а суть екрана.** Кожен сигнал
має ДВІ дії (`on_buy`, `on_sell`), і саме їхнє поєднання людина налаштовує:
«треугол на купівлю не так страшно, а на продаж — це вже інше». Показувати
одну дію означає сховати половину сенсу. У боті вони стоять поруч на одному
екрані навмисно — на сайті місця більше, тож тим паче.

Категорії згруповані так, як про них думає людина, а не як лежать у реєстрі:
`bot/keyboards/risk.py:CATEGORY_GROUPS` — брати звідти через API, не
перевигадувати.

### 2.2. BYOK — свої ключі до моделей

`bot/handlers/byok.py`, `core/storage/llm_keys_repo.py`. API немає.

| Ендпоїнт | Що кличе |
|---|---|
| `GET /user/llm-keys` | `list_llm_keys` — **уже маскує ключ**, сирого не віддає ніколи |
| `POST /user/llm-keys/{provider}` | `save_llm_key` |
| `DELETE /user/llm-keys/{provider}` | `delete_llm_key` + `drop_personal_verdicts` |
| `GET/POST /user/llm-keys/mode` | `get_byok_mode` / `set_byok_mode` |
| `POST /merchant/{exchange}/{id}/recheck` | те саме, що кнопка «🔑 Buy AI» в алерті |

**Межі, які не можна перейти на фронті:**

* ключ ніде не показується цілком — ані після збереження, ані в списку;
* поле вводу — `type="password"`, `autocomplete="off"`, значення не лягає в
  стан застосунку довше, ніж триває сабміт;
* ключ **ніколи** не потрапляє в URL, лог, аналітику чи повідомлення про
  помилку;
* без ключа сайт має працювати рівно як раніше. Базовий вердикт за BYOK
  ховати не можна ніколи — інакше це вже інша угода з користувачем, ніж та,
  на яку він підписувався.

Режим за замовчуванням — `ondemand`. Не міняти на `always` «для зручності»:
чужа квота не те, що можна почати витрачати за людину мовчки.

### 2.3. Вижимка умов переліком фактів (`terms_facts`)

Зараз сайт показує `ai.termsSummary` — один абзац
(`src/components/RiskPanel.tsx:118`). Бек уже вміє краще: перелік
`{topic, quote, meaning}` із **дослівною цитатою**, звіреною з оригіналом
механічно (`core/workers/terms_facts.py`). Непідтверджена цитата не
викидається, а позначається `⚠️`.

`terms_summary` лишається й далі заповнюється — саме щоб дашборд не зламався
мовчки. Тобто перенесення безпечне й робиться в свій час.

**API:** `_ai_view` (`api/verdict_refresh.py:60`) розпаковує кортеж із
п'яти полів і `terms_facts` туди не бере. Треба додати — джерело
`MerchantRepo.get_verdict_extras`.

**UI:** перелік із цитатою під кожним пунктом і видимою позначкою про
непідтверджені («1 з 5 — цитату не знайдено в умовах дослівно»). Позначка не
косметична: це єдине місце, де видно, що модель щось додала від себе.

### 2.4. Хід думок моделі (`thought_process`)

Нове поле в `merchant_verdict`, у боті під окремим тумблером
`show_ai_thoughts` (вимкнений за замовчуванням — у парному алерті блок іде
двічі, а в Telegram ліміт 4096). **На сайті цього обмеження немає**, тож
тут він доречніший, ніж у боті — під розгортанням.

`DisplayPayload` (`api/routers/control.py:600`) поля `showAiThoughts` не
має. Додати. Merge у `POST /user/display` значення не затирає, тож наявні
користувачі не постраждають.

### 2.5. Покриття — «на що ми дивились, а на що ні»

`core/engine/risk_coverage.py`. У боті це рядок «❔ НЕ ПЕРЕВІРЕНО: поведінка
— замало історії (1 із 3 снапшотів); клонів на інших біржах не шукали».

На сайті немає. Це не дрібниця: без нього «нічого не знайдено» і
«не перевіряли» виглядають однаково — головна помилка, від якої чистився
весь етап 0.

`RiskCoverage.gaps()` уже віддає готовий список людською мовою. Не
перекладати його на фронті — віддати через API як є.

## 3. Що вже віддається, але не показується

### 3.1. `reviewsSeen` / `reviewsStatusLabel` (нові, `control.py:995`)

Нуль у відгуках означає дві протилежні речі: «скарг немає» і «ми їх не
бачили». Дашборд показує `reviewScore` / `reviewNegPct` і читає другий
випадок як перший.

Тепер поруч є `reviewsSeen: bool` і `reviewsStatusLabel` («немає сесії біржі
— відгуків не видно»). Коли `reviewsSeen === false`, цифри показувати не
можна — на їхньому місці має бути причина.

### 3.2. `reviewScore` нарешті не нуль

Його **не писав ніхто** — поле існувало, віддавалось в API і завжди
дорівнювало нулю. Тепер заповнює движок. Якщо на фронті є місце, де воно
вважалось «завжди 0», його треба перевірити.

### 3.3. `termsStatus` / `termsStatusLabel`

У типах є (`src/types.ts:417,419`) — перевірити, чи справді показується, чи
лише оголошено.

## 4. Пастки саме цього перенесення

**Один виклик — одна правда.** Персональне рішення про ордер дає
`risk_decision.decide(order, resolver, side)`. На сайті спокуса порахувати
«ну тут же видно, що BLOCK» у TS — і саме так з'явиться друга політика, яка
розійдеться з першою. `AlertDispatcher.wants_which` уже викликається з
`api/routers/dashboard.py:142` — це правильний зразок.

**Прапори не парсити рядком.** `order.risk_flag` — рядок, склеєний комами, і
підрядковий пошук на ньому вже коштував нам режимів «попереджати»/«показувати»
(`"BLOCK" in "FOP_TOV_BLOCKED"`). На беку для цього є
`core/engine/risk_report.py` — віддавати фронту розібрану структуру, а не
рядок.

**Порожній список ≠ безпечно.** Ані на беку, ані на фронті. Якщо прапорів
немає, це «нічого не спрацювало»; що саме перевірили — каже покриття.

**Не показувати вижимку, зроблену наосліп.** `_drop_blind_terms` і
`_drop_blind_reviews` (`api/verdict_refresh.py`) уже прибирають вижимку,
коли джерела не видно. Будь-яке нове поле з кешу вердиктів (`terms_facts`,
`thought_process`) потребує того самого захисту — інакше воно опише те,
чого ми зараз не бачимо, і подасть це як поточний стан.

**PageSpeed.** У проєкту є бюджет швидкості лендингу (100/99): без сторонніх
шрифтів, без `opacity:0` на кореневих блоках, контраст від slate-400. Екрани
дашборда за логіном під цей бюджет не підпадають, але лендинг — так.

## 5. Порядок

```
1. Прибрати riskMode (він зламаний прямо зараз)
2. Показати те, що вже віддається: reviewsSeen, reviewScore, termsStatus
3. API + екран ріск-енджину (профіль → політика → власні сигнали)
4. terms_facts у картці мерчанта
5. Покриття в картці
6. BYOK: ключі, режим, перевірка на вимогу
7. thought_process під розгортанням
```

Пункти 1–2 самодостатні й дають ефект одразу. Пункт 3 найбільший; без нього
конфігуратор лишається тільки в боті, і це нормальний проміжний стан.
