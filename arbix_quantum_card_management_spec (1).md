## ЧАСТИНА 1 — АРХІТЕКТУРА БАЗИ ДАНИХ (Firebase Firestore)

Уся система побудована на принципі **мультиюзерності (Multi-tenancy)**: кожен запит до БД обов'язково фільтрується за `owner_id` (Telegram ID користувача). Ніяких ситуацій, коли один юзер бачить карти іншого.

---

### 1.1. Колекція `users`

Зберігає профіль кожного користувача бота та його глобальні налаштування. Ці налаштування є **дефолтними** для всіх карт, поки картка не має власних індивідуальних налаштувань.

**Поля:**

- `user_id` — String. Telegram ID. Є первинним ключем.
- `merchant_filters` — Array of Strings. Фільтри мерчантів, наприклад: `["no_pumb", "only_verified"]`. Використовується Matching Engine'ом для відсіву карт.
- `max_cards_per_order` — Integer. Максимальна кількість карт, які бот може залучити до одного ордеру при спліті. Наприклад, якщо стоїть `2`, бот не запропонує спліт на 3 карти, а просто скаже що лімітів немає.
- `global_bank_limits` — Object. Глобальні правила для кожного банку. Якщо карта не має `is_custom_limits == true`, вона наслідує ці правила. Структура по кожному банку:
  - `daily_vol_max` — максимальний денний оборот (грн)
  - `monthly_vol_max` — максимальний місячний оборот (грн)
  - `max_single_tx` — максимальна сума однієї транзакції (наприклад, для ПриватБанку — 29 999 грн)
  - `max_tx_count_daily` — максимальна кількість транзакцій на день (важливо: банки блокують за аномальну кількість дрібних переказів, навіть якщо об'єм невеликий)
  - `cooldown_hours` — рекомендований час відпочинку після вичерпання карти (наприклад, 24 або 48 годин)

**Приклад `global_bank_limits`:**
```json
{
  "monobank": {
    "daily_vol_max": 150000,
    "monthly_vol_max": 400000,
    "max_single_tx": 49999,
    "max_tx_count_daily": 15,
    "cooldown_hours": 24
  },
  "privatbank": {
    "daily_vol_max": 100000,
    "monthly_vol_max": 300000,
    "max_single_tx": 29999,
    "max_tx_count_daily": 10,
    "cooldown_hours": 48
  }
}
```

### 1.2. Колекція `cards`

Головна колекція системи. Кожен документ — одна карта.

**ВАЖЛИВО З БЕЗПЕКИ:** Ніколи не зберігати повний PAN (номер картки), термін дії та CVV. Тільки ідентифікатори для операційних потреб.

**Поля:**

- `card_id` — String. Унікальний UUID, генерується при додаванні.
- `owner_id` — String. Telegram ID власника. Обов'язковий фільтр у всіх запитах.
- `bank_name` — String. Назва банку: `monobank`, `privatbank`, `pumb`, `sense`, `abank` тощо.
- `last_four` — String. Останні 4 цифри картки (`*4321`). Тільки для візуальної ідентифікації.

**Блок `metadata` — ідентифікація картки:**
- `is_own` — Boolean. `true` = картка твоя особиста. `false` = стороння (дроп, родич, друг).
- `category` — String. Уточнюючий тип: `self`, `relative`, `friend`, `trusted_drop`, `public_drop`.
- `label` — String (необов'язково). Власна мітка-бадж користувача: "Карта мами", "Дроп Саня", "Карта для тестів". Може бути як обрана з заготовлених, так і повністю кастомна.
- `note` — String (необов'язково). Довільна текстова примітка: "тільки денні ліміти", "не використовувати після 22:00", "ліміти порізані банком". Примітки доступні як для чужих карт, так і для своїх.

**Блок `settings` — налаштування лімітів:**
- `is_custom_limits` — Boolean. Якщо `true`, карта використовує власні ліміти (`limits_override`) замість глобальних налаштувань банку з профілю юзера. Це потрібно для випадків, коли банк "порізав" ліміти конкретному акаунту, і треба прописати реальні цифри індивідуально.
- `limits_override` — Object (заповнюється тільки якщо `is_custom_limits == true`). Структура ідентична `global_bank_limits` для одного банку: `daily_vol_max`, `monthly_vol_max`, `max_single_tx`, `max_tx_count_daily`, `cooldown_hours`.

**Логіка наслідування лімітів (в Python):**
```python
limit = card.limits_override if card.is_custom_limits else user.global_bank_limits[card.bank_name]
```

**Блок `current_state` — поточний стан:**
- `balance` — Number. Поточний фіатний залишок на карті (грн). Оновлюється через API або вручну. Необхідний для перевірки при операціях на вивід (Maker Sell).
- `used_daily_vol` — Number. Скільки грн вже прокручено сьогодні (і робочі, і особисті транзакції — бо фінмоніторингу байдуже, на що витрачені гроші).
- `used_monthly_vol` — Number. Аналогічно по місяцю.
- `tx_count_today` — Number. Кількість транзакцій сьогодні. Враховуються всі операції.
- `last_tx_timestamp` — Timestamp. Час останньої операції. Потрібен для:
  - розрахунку "липкості" (Stickiness) в Scoring Engine
  - розрахунку рекомендованого часу відпочинку
  - аналізу активності карти
- `status` — String. Поточний стан: `active`, `cooldown` (відпочиває), `blocked`.
- `cooldown_until` — Timestamp (заповнюється, якщо `status == cooldown`). Час, до якого карта не береться в розрахунок сканером.

---

### 1.3. Колекція `orders`

Лог усіх робочих сесій. Кожен ордер прив'язаний до юзера і до карт.

**Поля:**

- `order_id` — String. Унікальний UUID.
- `owner_id` — String. Telegram ID.
- `total_amount` — Number. Загальна сума ордеру.
- `target_bank` — String. Банк, потрібний для цього ордеру.
- `status` — String: `pending` (зарезервовано, очікує), `completed` (успішно закрито), `canceled` (скасовано).
- `split_strategy` — Array. Масив карт, задіяних в ордері:
  ```json
  [
    {"card_id": "uuid1", "amount": 20000},
    {"card_id": "uuid2", "amount": 30000}
  ]
  ```
- `expected_window_minutes` — Integer. Вікно очікування (хвилин), протягом якого вхідна транзакція вважається "робочою" для цього ордеру. Зазвичай 15–30 хвилин.
- `created_at` — Timestamp.
- `completed_at` — Timestamp.

---

### 1.4. Колекція `transactions`

Лог усіх транзакцій по кожній карті.

**Поля:**

- `tx_id` — String.
- `card_id` — String. Прив'язка до карти.
- `owner_id` — String.
- `amount` — Number.
- `direction` — String: `in` (прихід), `out` (витрата).
- `type` — String: `work` (арбітражна) або `personal` (особиста/побутова).
- `linked_order_id` — String (якщо `type == work`). Прив'язка до ордеру.
- `timestamp` — Timestamp.
- `source` — String: `webhook_mono`, `push_forwarder`, `manual` — звідки прийшло підтвердження.

## ЧАСТИНА 2 — MATCHING ENGINE (Ядро підбору карти)

Це найважливіший модуль. Коли сканер знаходить спред, він передає параметри до `ArbixMatchingEngine`, який проводить підбір карти через чотириетапний пайплайн: **Fetch → Filter → Score → Select/Split**.

---

### 2.1. Fetch (Оптимізований запит до Firebase)

Перший фільтр робиться ще на рівні БД, щоб не читати зайві документи (Firebase тарифікує за reads):

```python
query = cards_ref
    .where('owner_id', '==', user_id)
    .where('bank_name', '==', target_bank)
    .where('current_state.status', '==', 'active')
```

Тобто до пам'яті потрапляють тільки активні карти потрібного банку конкретного юзера.

---

### 2.2. Hard Filters (Жорсткий відсів — локально в Python)

Карта відкидається якщо хоч одна умова не виконана:

1. **Ліміт денного обороту:** `(daily_vol_max - used_daily_vol) >= order_amount`
2. **Ліміт місячного обороту:** `(monthly_vol_max - used_monthly_vol) >= order_amount`
3. **Ліміт однієї транзакції:** `max_single_tx >= order_amount`
   - Якщо ця умова не виконана, але по обороту карта ще живе → карта не викидається повністю, а відправляється до Split Engine з міткою "потребує розбивки"
4. **Кількість транзакцій:** `tx_count_today < max_tx_count_daily`
5. **Баланс (для операцій на вивід):** `balance >= order_amount`
6. **Фільтри мерчанта:** Якщо у мерчанта є правило "не приймати з ПУМБ" або "тільки верифіковані" — карти, що не проходять, відсіваються.

---

### 2.3. Scoring (Система балів — пріоритетизація)

Кожна карта, що пройшла Hard Filters, отримує числовий `score`. Базовий score = 100.

**Бонусні бали:**

| Умова | Бали | Пояснення |
|---|---|---|
| `card.is_own == False` (дроп/родич) | +50 | Дропові карти використовуємо в першу чергу, свої бережемо |
| Карта використовувалась протягом останніх 60 хвилин | +30 | "Липкість" — краще добити одну карту, ніж світити 5 різних перед фінмоном |
| Залишилось менше 10% денного ліміту (і сума туди влазить) | +40 | Добиваємо до кінця і відправляємо на cooldown |

**Штрафні бали:**

| Умова | Бали | Пояснення |
|---|---|---|
| `tx_count_today >= max_tx_count_daily - 2` | -60 | Карта майже вичерпала транзакційний ліміт, краще дати перепочити |
| Картка була на cooldown протягом останніх 24 год і тільки нещодавно стала active | -20 | Даємо трохи "охолонути" після відпочинку |

Після розрахунку балів карти сортуються за спаданням score. Береться `cards[0]`.

---

### 2.4. Split Engine (Якщо одна карта не покриває суму)

Вмикається у двох випадках:
1. Після Hard Filters список карт порожній (немає жодної, що покриває суму цілком).
2. Є карти, але сума перевищує `max_single_tx` на кожній з них (потрібна розбивка навіть по одній картці).

**Логіка Split Engine:**

1. Беремо всі активні карти потрібного банку юзера.
2. Алгоритм шукає **мінімальну** кількість карт, необхідних для покриття суми ордеру. Пріоритет: 2 карти по 25к краще ніж 5 карт по 10к — менше транзакцій = менше підозр від фінмону.
3. При виборі пар/трійок — пріоритет картам, де залишилось мало ліміту (щоб закрити їх і відправити на відпочинок).
4. Формується об'єкт `SuggestedSplit`:

```python
{
  "order_id": "uuid",
  "total_amount": 50000,
  "split": [
    {"card_id": "card_1", "amount": 30000, "label": "Моно (своя *4321)"},
    {"card_id": "card_2", "amount": 20000, "label": "Приват (Дроп Саня *8812)"}
  ]
}
```

5. Бот пропонує цей спліт юзеру через Inline-кнопки.
6. Юзер може натиснути "Інший варіант" — тоді Engine генерує наступну комбінацію.

**Важливо — "Внутрішній спліт" по одній карті:**
Якщо картка Привату має 60к вільного ліміту, але `max_single_tx = 29999`, і ордер на 50к — бот може запропонувати провести **дві транзакції з однієї картки**: 29к + 21к. Це окремий підкейс Split Engine.

---

### 2.5. Атомарність операцій у Firebase

Коли підтверджується спліт (і резервується сума з кількох карт), оновлення лімітів усіх карт відбувається **одночасно** через `firestore.Transaction`. Якщо хоча б одна карта не оновилась (помилка мережі, гонка запитів) — весь ордер відкочується і лімітів не списується.

---

### 2.6. Резервування (Reserved State)

Щоб уникнути ситуації, коли два ордери "захоплюють" один і той самий ліміт одночасно (Concurrency), при підтвердженні ордеру стан карти змінюється на `reserved` до закриття ордеру. Решта ордерів не можуть використовувати зарезервовану суму.

## ЧАСТИНА 3 — ОБРОБКА ТРАНЗАКЦІЙ ТА АВТОМАТИЗАЦІЯ

---

### 3.1. Стратегія підключення банків до системи

**Monobank (Пріоритет #1):**
Єдиний банк з нормальним офіційним Personal API. Потрібно:
1. Зареєструвати API-токен через особистий кабінет Mono.
2. Вказати webhook-URL, куди Mono буде надсилати сповіщення про кожну транзакцію в реальному часі.
3. Python-скрипт слухає цей webhook і миттєво оновлює дані в Firebase.

**ПриватБанк та інші (Workaround):**
Офіційного API для фізосіб немає. Два варіанти:
- **Android Push/SMS Forwarder:** Додаток на телефоні перехоплює Push-сповіщення від банківського додатку і пересилає текст у Telegram-бот або на API сканера.
- **Ручне введення:** Юзер підтверджує транзакцію кнопкою в боті.

**ВАЖЛИВО — Анти-фрод:**
Бот **ніколи** не підтверджує транзакцію на основі тексту SMS чи Push. Все, що від SMS/Push — це лише сигнал "перевір". Реальне підтвердження — це зміна балансу через API (для Mono) або свідоме натискання кнопки "Підтвердити" юзером. Якщо API каже, що баланс не змінився — транзакція фейкова, ордер не закривається.

---

### 3.2. Вікно очікування: Робочі vs Особисті транзакції

Це механізм, який автоматично розділяє арбітражні транзакції від буденних витрат.

**Як це працює:**

1. Коли юзер бере ордер "в роботу", в колекції `orders` створюється запис зі статусом `pending` і полями: `total_amount`, `target_bank`, `split_strategy`, `expected_window_minutes`.
2. Коли приходить webhook або Push від банку, Python перевіряє:
   - Чи є активний `pending` ордер для цієї карти?
   - Чи сума транзакції співпадає з очікуваною (або з частиною спліту)?
   - Чи транзакція прийшла в межах `expected_window_minutes`?
3. Якщо всі три умови виконані → транзакція маркується як `work`, ордер закривається, ліміти списуються, в арбітражну статистику іде плюс.
4. Якщо хоча б одна умова не виконана → транзакція маркується як `personal`. Вона все одно збільшує `used_daily_vol` і `used_monthly_vol` (бо фінмоніторинг бачить всі гроші), але не впливає на арбітражну статистику і не закриває ордери.

**Чому враховувати особисті транзакції — це ПЛЮС:**
Банківський фінмоніторинг аналізує профіль клієнта. Якщо по картці йдуть тільки "круглі" суми без жодної оплати в магазинах — це "червоний прапор". Система, яка враховує побутові витрати, дає реальну картину залишку ліміту і дозволяє будувати "природній" профіль транзакцій.

---

### 3.3. Логіка Cooldown (Відпочинок карти)

Після інтенсивного використання карта повинна "відпочити", щоб не привертати увагу фінмону.

Тригери для автоматичного переводу в `cooldown`:
1. `used_daily_vol >= daily_vol_max * 0.95` (вичерпано 95% денного ліміту)
2. `tx_count_today >= max_tx_count_daily` (вичерпано ліміт транзакцій)
3. Вручну юзер переводить карту в cooldown кнопкою в боті

При переводі в `cooldown`:
- `status` стає `cooldown`
- `cooldown_until` = `now + cooldown_hours` (з налаштувань банку або індивідуальних)
- Бот сповіщає юзера: "Картка Моно (*4321) відправлена на відпочинок до [дата/час]"

Щоночі (або при кожному зверненні до карти) — перевіряємо чи минув `cooldown_until`. Якщо так → `status` повертається до `active`, `used_daily_vol` та `tx_count_today` скидаються до 0.

---

### 3.4. Щоденний скид лімітів

О опівночі (або при першому зверненні після 00:00) для кожної карти:
- `used_daily_vol` → 0
- `tx_count_today` → 0
- `status` (якщо `cooldown` і `cooldown_until` вже минув) → `active`

Місячні ліміти (`used_monthly_vol`) скидаються 1-го числа кожного місяця.

## ЧАСТИНА 4 — TELEGRAM BOT MVP (Інтерфейс)

---

### 4.1. Додавання та управління картами (CRUD)

**Команда `/add_card` — Інтерактивний діалог:**
1. Бот запитує: "Це ваша картка чи стороння?" → Inline-кнопки: [Моя] [Стороння]
2. Якщо "Стороння" → бот автоматично присвоює базовий статус `drop`, але одразу пропонує уточнення: [Родич] [Друг] [Дроп] [Ввести своє]
3. Бот запитує банк → список кнопок: [Monobank] [PrivatBank] [PUMB] [Sense] [Інший]
4. Бот запитує: "Введіть останні 4 цифри картки"
5. Бот запитує: "Введіть мітку (або пропустіть)" → опціонально
6. Запитує: "Введіть примітку (або пропустіть)" → опціонально
7. Бот запитує: "Використати глобальні ліміти банку, чи встановити індивідуальні?" → [Глобальні] [Індивідуальні]

## ЧАСТИНА 6 — НЮАНСИ ТА ВАЖЛИВІ ДЕТАЛІ

### 6.1. Про особисті транзакції та основну картку

Якщо основна картка (своя) використовується і для арбітражу, і для побуту — це нормально і навіть корисно. Побутові транзакції знижують "підозрілість" профілю клієнта для банківського антифроду. Система все одно вираховує реальний залишок ліміту, включаючи всі типи витрат.

### 6.2. Про ліміти банків

Кожен банк має свої правила, які можуть відрізнятись:
- Monobank: ~150к грн/міс на перекази між фізособами
- PrivatBank: негласне правило — не більше 29 999 грн однією транзакцією
- ПУМБ, А-Банк: агресивний моніторинг на кількість дрібних переказів

Всі ці правила зберігаються в `global_bank_limits` і можуть бути оновлені юзером через бота при зміні умов банку.

### 6.3. Про мітки та категорії карт

Система маркування вирішує когнітивне навантаження при масштабуванні. При 10+ картах неможливо пам'ятати "чия це Моно *8812". Бадж "Дроп від Сані" одразу дає розуміння рівня довіри, типу лімітів і того, як поводитись з цією карткою.

Ієрархія маркування:
1. `is_own` — базовий поділ (моя / чужа)
2. `category` — тип відносин (self / relative / friend / drop)
3. `label` — коротка мітка (відображається в повідомленнях бота)
4. `note` — довга примітка (відображається при деталях картки)

### 6.4. Про готовність до автотрейду

Вся архітектура свідомо проектується так, щоб перехід до автоматичного виконання ордерів вимагав **мінімуму змін**:
- Matching Engine вже написаний як незалежний клас
- Логіка ордерів вже зберігає всю потрібну інформацію
- При автотрейді просто прибирається крок ручного підтвердження ("Взяти в роботу") — решта логіки залишається незмінною

## ЧАСТИНА 7 — РЕЖИМИ ВМИКАННЯ/ВИМИКАННЯ МОДУЛЯ КАРТ

### 7.1. Три рівні роботи модуля

Модуль карт не є обов'язковим для використання. Юзер може мати прив'язані карти, але не хотіти щоб бот їх "чіпав" в алертах. Тому вводиться три режими замість простого on/off.

**Поле в колекції `users`:**
`card_module_mode` — String: `"off"` | `"track_only"` | `"full"`

---

**Режим `"off"` — Повне вимкнення:**
- Карти можуть бути прив'язані до акаунту і зберігатись у Firestore
- Якщо є активний webhook (наприклад, Monobank API) — транзакції все одно можуть логуватись пасивно
- Але бот **жодним чином** не згадує карти в алертах, командах і підказках
- Matching Engine взагалі не запускається
- Корисно: юзер ще не налаштував карти, або просто не хоче цей функціонал зараз

**Режим `"track_only"` — Тільки трекінг:**
- Карти прив'язані, ліміти оновлюються в БД (через webhook або вручну)
- Статистика накопичується (оберти, транзакції, cooldown-рекомендації)
- В алертах про знайдений спред **не виводиться** блок рекомендованої карти/спліту
- Юзер самостійно вирішує яку карту брати — бот не втручається
- Команди `/cards` та `/report` продовжують працювати — юзер може переглянути стан карт вручну
- Корисно: коли хочеш самостійно контролювати вибір, але мати актуальну статистику під рукою

**Режим `"full"` — Повний функціонал:**
- Карти трекаються повністю
- В алерті про знайдений спред виводиться блок рекомендованої карти або спліту
- Доступні Inline-кнопки "Взяти в роботу", "Підтвердити", "Інша картка" прямо з алерту
- Весь робочий процес автоматизований

### 7.2. Інтеграція з існуючими налаштуваннями алерту

В боті вже є меню налаштувань додаткової інформації в повідомленні про спред. Пункт керування картами додається туди як ще один рядок. Варіанти відображення:

## ЧАСТИНА 8 — НАПРЯМКИ ФІАТУ: П'ЯТЬ РЕЖИМІВ РОБОТИ БОТА

Це критично важлива частина, яка змінює логіку Matching Engine в залежності від того, як рухається фіат.

Крипта знаходиться на гаманцях (біржа/wallets), а не на картах — тому карти відповідають **виключно за фіатну сторону** угоди. Але в кожному з п'яти режимів фіат рухається по-різному.

### 8.1. Таблиця напрямків фіату по режимах

| Режим | Що відбувається з фіатом | Що перевіряє Engine |
|---|---|---|
| **SPREAD** (buy + sell одночасно) | BUY-нога: фіат **виходить** з карти → крипта на гаманець; SELL-нога: крипта з гаманця → фіат **приходить** на карту | Дві перевірки: карта на вихід (баланс + out-ліміти) + карта на прийом (in-ліміти + whitelist банку) |
| **Taker Buy** (тільки купівля) | Фіат **виходить** з карти → крипта на гаманець | Баланс + outgoing ліміти + `max_single_tx_out` |
| **Taker Sell** (тільки продаж) | Крипта з гаманця → фіат **приходить** на карту | Incoming ліміти + чи може карта приймати + bank whitelist мерчанта |
| **Maker Buy** (виставляємо ордер на купівлю) | Ти відправляєш фіат продавцю | Баланс + outgoing ліміти + `max_single_tx_out` |
| **Maker Sell** (виставляємо ордер на продаж) | Покупець відправляє тобі фіат на карту | Incoming ліміти + bank whitelist мерчанта (це фільтр для **твоєї** приймаючої карти) |

---

### 8.2. Оновлена структура `current_state` в колекції `cards`

Додається роздільне трекування приходів і витрат — бо банківський фінмоніторинг рахує їх незалежно:

```json
"current_state": {
  "balance": 45000,
  "used_daily_out": 12000,
  "used_daily_in": 8000,
  "used_monthly_out": 85000,
  "used_monthly_in": 60000,
  "tx_count_today": 5,
  "tx_out_today": 3,
  "tx_in_today": 2,
  "last_tx_timestamp": 1713370000,
  "status": "active",
  "cooldown_until": null
}
```

**Поля:**
- `used_daily_out` — скільки фіату вийшло з картки сьогодні (оплати, перекази іншим)
- `used_daily_in` — скільки фіату прийшло на картку сьогодні (отримані перекази)
- `used_monthly_out` / `used_monthly_in` — аналогічно по місяцю
- `tx_out_today` — кількість вихідних транзакцій сьогодні
- `tx_in_today` — кількість вхідних транзакцій сьогодні
- `tx_count_today` — загальна сума (in + out), для загального ліміту транзакцій банку

---

### 8.3. Оновлена структура `limits` в `settings` картки

Ліміти також розділяються на incoming та outgoing, бо деякі банки (наприклад, Monobank) мають різні обмеження на відправку і отримання:

```json
"limits": {
  "daily_out_max": 150000,
  "daily_in_max": 150000,
  "monthly_out_max": 400000,
  "monthly_in_max": 400000,
  "max_single_tx_out": 49999,
  "max_single_tx_in": 49999,
  "max_tx_per_day": 15
}
```

Ці поля є як у `global_bank_limits` (в колекції `users`), так і в `limits_override` (якщо `is_custom_limits == true`). Логіка наслідування не змінюється.

---

### 8.4. Оновлена логіка Matching Engine по напрямку

Engine тепер отримує параметр `direction` при кожному виклику.

**Для BUY-ноги (вихідний фіат) — `direction = "buy"`:**
```
1. card.balance >= order.amount
2. (daily_out_max - used_daily_out) >= order.amount
3. (monthly_out_max - used_monthly_out) >= order.amount
4. max_single_tx_out >= order.amount
5. tx_out_today < (max_tx_per_day / 2)  — приблизний half-limit
6. Scoring → видати карту або запустити Split
```

**Для SELL-ноги (вхідний фіат) — `direction = "sell"`:**
```
1. card.status == "active"
2. card.bank_name є у bank_whitelist мерчанта
3. (daily_in_max - used_daily_in) >= order.amount
4. (monthly_in_max - used_monthly_in) >= order.amount
5. max_single_tx_in >= order.amount
6. tx_in_today < (max_tx_per_day / 2)
7. Scoring → видати карту або запустити Split
```

**Для SPREAD-режиму — `direction = "spread"`:**
Engine запускається **двічі послідовно**:
1. Перший запуск: `direction = "buy"` → знаходить карту для оплати (BUY-нога)
2. Другий запуск: `direction = "sell"` → знаходить карту для прийому (SELL-нога)
3. Перевірка: бажано щоб це не була одна й та сама карта (хоча технічно можливо)
4. В алерті виводяться два окремих блоки:

```
📊 ЗНАЙДЕНО СПРЕД | Сума: 45 000 грн

💸 ЧИМ ПЛАТИМО (BUY-нога):
💳 Моно (Дроп Саня *4321) | Вільно: 73к | 4/15 транзакцій

📥 НА ЩО ПРИЙМАЄМО (SELL-нога):
💳 Приват (Своя *8812) | Вільно на прийом: 95к | 2/10 транзакцій

[✅ Взяти в роботу] [🔄 Інші картки] [❌ Скасувати]
```

### 8.5. Про Maker Sell і bank_whitelist

Важливий нюанс: в режимі **Maker Sell** фільтр `bank_whitelist` мерчанта — це вимога до **твоєї картки**, на яку ти приймаєш гроші від покупця. Тобто якщо мерчант (покупець) написав "приймаю тільки на Monobank і PrivatBank" — бот фільтрує твої карти і пропонує тільки ті, що підходять під цю вимогу.

Це відрізняється від загального розуміння "фільтрів мерчанта" — тут мова не про картку контрагента, а про твою власну.

### 8.6. Про крипту та перевірку `crypto_available`

Криптогаманці **не входять** в card management module — баланс крипти вже відстежується в існуючій логіці сканера (через API біржі або balance check).

Але перед запуском Matching Engine для будь-якої SELL або SPREAD ноги необхідна одна попередня перевірка: **чи є достатньо крипти на гаманці для виконання угоди**. Ця перевірка відбувається ззовні card module і передається як вхідний параметр:

```python
engine = ArbixMatchingEngine(
    user_id=user_id,
    bank=target_bank,
    amount=order_amount,
    direction="sell",
    crypto_available=True   # передається зі scanner-логіки
)
```

Якщо `crypto_available = False` → Matching Engine для sell/spread не запускається взагалі, алерт або не відправляється, або відправляється без блоку рекомендації карти для SELL-ноги.

### 9.1. Rolling 24-годинне вікно vs Midnight Reset

**Проблема з midnight reset:**
Якщо просто скидати `used_daily_out/in` о 00:00, то юзер може провести велику серію транзакцій о 23:50, а вже о 00:01 всі ліміти чисті і можна повторювати. Це саме та поведінка, яку банківський антифрод відловлює — аномальний оборот у короткий проміжок часу через перехід доби.

**Рішення — Rolling 24-годинне вікно:**
Замість скидання по календарній добі, ліміти рахуються за **останні 24 години від поточного моменту**. Тобто "денний ліміт" — це сума транзакцій між `(now - 24h)` і `now`, а не між `00:00` і `23:59`.

**Як реалізувати в Python без перебору всіх транзакцій:**
Оскільки зберігати і перераховувати всі транзакції за 24 год при кожному запиті — дорого (Firebase reads), використовуємо підхід через **sliding bucket**:

```python
# В current_state зберігаємо не просто суму, а масив "відрізків"
# Кожен відрізок — це {timestamp, amount_out, amount_in, tx_count}
# При кожному зверненні — викидаємо записи старіші за 24 год, рахуємо суму решти

def get_rolling_used(card, direction: str, hours: int = 24) -> float:
    cutoff = datetime.now() - timedelta(hours=hours)
    recent = [t for t in card.tx_buckets if t['timestamp'] > cutoff]
    return sum(t[f'amount_{direction}'] for t in recent)
```

**Що зберігається в `current_state.tx_buckets`:**
```json
"tx_buckets": [
  {"timestamp": 1713370000, "amount_out": 15000, "amount_in": 0, "tx_count": 1},
  {"timestamp": 1713375000, "amount_out": 0, "amount_in": 20000, "tx_count": 1}
]
```

Старіші 24 год записи видаляються при кожному оновленні картки (lazy cleanup).

**Місячний ліміт** — тут rolling вікно не потрібне. Банки рахують по календарному місяцю (1-го числа скид). Тому `used_monthly_out/in` скидається 1-го числа (lazy або cron — деталі в п.9.8).

### 9.2. Нотіфка при вичерпанні картки (Event-driven, не спам)

**Проблема:**
Якщо перевіряти ліміти при кожному скані і кожного разу надсилати повідомлення "картка майже вичерпана" — юзер отримає десятки однакових сповіщень за хвилину.

**Рішення — One-shot флаги:**
В `current_state` кожної картки зберігаються флаги відправлених нотіфок. Як тільки поріг пройдено — флаг ставиться, і повторна нотіфка не надсилається до наступного скидання ліміту.

**Нові поля в `current_state`:**
```json
"notification_flags": {
  "notified_80pct_out": false,
  "notified_95pct_out": false,
  "notified_80pct_in": false,
  "notified_95pct_in": false,
  "notified_tx_limit": false,
  "notified_empty": false
}
```

**Логіка спрацювання (перевіряється після кожної транзакції):**

| Умова | Флаг | Повідомлення юзеру |
|---|---|---|
| `used_daily_out >= daily_out_max * 0.80` | `notified_80pct_out` | 🟡 Моно (*4321): 80% вихідного ліміту використано |
| `used_daily_out >= daily_out_max * 0.95` | `notified_95pct_out` | 🔴 Моно (*4321): 95% вихідного ліміту. Рекомендую cooldown |
| `tx_count_today >= max_tx_per_day` | `notified_tx_limit` | ⛔ Моно (*4321): ліміт транзакцій вичерпано, карта йде на cooldown |
| `used_daily_out >= daily_out_max` | `notified_empty` | ⛔ Моно (*4321): денний ліміт вичерпано |

**Скидання флагів:** разом зі скиданням `tx_buckets` (коли sliding window "очищається") всі `notification_flags` скидаються до `false`. Для місячних порогів аналогічно — скидання 1-го числа.

**Важливо — переход "були карти → нема карт":**
Окремий критичний event: якщо Matching Engine провів Hard Filter і **жодна карта не пройшла** для конкретного банку — юзер отримує одну нотіфку:
```
⚠️ Немає доступних карт для Monobank.
Причини: Mono (*4321) — ліміт вичерпано. Mono (*5566) — cooldown до 18:00.
Для цього банку ордери тимчасово недоступні.
```
Ця нотіфка надсилається **один раз** при першому ж скані, де всі карти відсіялись. Повторно — тільки якщо ситуація змінилась (картка стала active) і знову стала недоступною.
Флаг: `users.no_cards_notified[bank_name]: bool` — скидається, коли хоча б одна картка банку знову стає `active`.

### 9.3. Статус `partially_completed` для ордерів зі сплітом

**Проблема:**
При спліті (наприклад, 2 карти) може статись ситуація: перша транзакція пройшла успішно, а друга — ні (картку заблокували, таймаут, фейкова оплата). Ордер не можна закрити як `completed` і не можна скасувати як `canceled` — він у підвішеному стані.

**Рішення — новий статус `partially_completed`:**

Додати до поля `status` в колекції `orders` значення `partially_completed`.

**Flow при частковому виконанні спліту:**

```
1. Ордер зі сплітом [Картка А: 25000] + [Картка Б: 20000] створено → status: "pending"

2. Webhook підтвердив транзакцію по Картці А (25000 грн) → 
   - Ліміти Картки А оновлюються
   - В orders.split_strategy: [{card_id: A, amount: 25000, status: "done"}, 
                                {card_id: B, amount: 20000, status: "pending"}]
   - Загальний status ордеру: "partially_completed"

3а. Картка Б підтверджена → загальний status: "completed"
3б. Таймаут або картка заблокована → 
    - Бот нотіфікує юзера: 
      "⚠️ Ордер частково виконано. Картка Б (*8812) не підтверджена.
       Що робити? [💳 Обрати іншу карту] [❌ Скасувати залишок]"
    - Якщо юзер обирає "Іншу карту" → Split Engine запускається тільки на суму 20000
      і пропонує заміну для Картки Б
    - Якщо "Скасувати залишок" → status ордеру: "partially_completed" (фінальний),
      ліміти Картки А не повертаються (транзакція реально пройшла)
```

**Нові поля в `orders`:**
```json
"split_strategy": [
  {"card_id": "uuid_A", "amount": 25000, "leg_status": "completed"},
  {"card_id": "uuid_B", "amount": 20000, "leg_status": "pending"}
],
"status": "partially_completed",
"completed_amount": 25000,
"remaining_amount": 20000
```

**Таймаут для pending leg:**
Якщо нога спліту не підтверджена протягом `expected_window_minutes` — вона автоматично переходить в `leg_status: "timeout"` і юзер отримує нотіфку з варіантами дій.

### 9.4. Діагностичний вивід при відсутності підходящих карт

**Проблема:**
Якщо Matching Engine нічого не знайшов, просте "карт немає" — неінформативне. Юзер не розуміє, що виправити: поповнити баланс, дочекатись cooldown, чи взагалі додати нову карту.

**Рішення — Rejection Report:**
Engine при поверненні порожнього результату формує звіт по кожній картці, яка не пройшла, із конкретною причиною відхилення.

**Формат повідомлення:**
```
🔍 Підбір карти для Monobank | 45 000 грн | BUY

❌ Моно (Дроп Саня *4321) — вичерпано денний ліміт
   Використано: 148 000 / 150 000 грн

❌ Моно (Своя *8812) — сума перевищує max_single_tx
   Ліміт однієї транзакції: 30 000 грн (потрібно 45 000)

❌ Моно (Родич *5566) — карта на cooldown
   Доступна після: 17:30

💡 Варіант: Спліт із двох карт недоступний (загальний вільний ліміт: 2 000 грн)
```

**Як реалізувати в Engine:**
На етапі Hard Filters кожна відхилена картка додається до масиву `rejected_cards` з причиною:

```python
rejected_cards = []
for card in all_cards:
    reason = self._get_rejection_reason(card, amount, direction)
    if reason:
        rejected_cards.append({"card": card, "reason": reason})

def _get_rejection_reason(self, card, amount, direction) -> str | None:
    if card.status == "cooldown":
        return f"cooldown до {card.cooldown_until}"
    if card.balance < amount and direction == "buy":
        return f"недостатній баланс ({card.balance} < {amount})"
    if card.get_effective_limits().max_single_tx_out < amount:
        return f"max_single_tx = {card.get_effective_limits().max_single_tx_out}"
    if card.get_rolling_used("out") + amount > card.get_effective_limits().daily_out_max:
        used = card.get_rolling_used("out")
        max_l = card.get_effective_limits().daily_out_max
        return f"денний ліміт: {used}/{max_l} грн"
    return None  # карта проходить
```

Якщо результат порожній — `rejected_cards` передається в Telegram-повідомлення замість стандартного "немає карт".

### 9.5. Конфлікт фільтрів банків

**Проблема:**
Юзер в налаштуваннях сканера виставив `buy_banks = [Monobank, PrivatBank]`, але серед прив'язаних карт немає жодної карти цих банків (або всі вони в cooldown/blocked). Сканер знаходить спреди, але Matching Engine завжди порожній. Юзер не розуміє чому сигналів немає.

**Рішення — перевірка конфлікту при зміні фільтрів:**

Коли юзер змінює `buy_banks` або `sell_banks` в налаштуваннях сканера — система одразу перевіряє наявність активних карт по кожному банку зі списку:

```python
def check_filter_card_conflict(user_id, banks: list) -> list:
    conflicts = []
    for bank in banks:
        active_cards = db.get_active_cards(user_id, bank)
        if not active_cards:
            all_cards = db.get_all_cards(user_id, bank)
            if not all_cards:
                conflicts.append({"bank": bank, "reason": "no_cards_added"})
            else:
                cooldown_until = min(c.cooldown_until for c in all_cards if c.status == "cooldown")
                conflicts.append({"bank": bank, "reason": "all_on_cooldown", "until": cooldown_until})
    return conflicts
```

**Повідомлення при конфлікті (надсилається одразу при збереженні фільтру):**
```
⚠️ Конфлікт фільтрів:

Monobank — немає доданих карт
  → Додайте картку: /add_card

PrivatBank — всі карти на cooldown
  → Карта (*4321) доступна після 18:30
```

**Додатково — перевірка при старті сканування:**
Якщо юзер запускає сканер при активному конфлікті — бот попереджає, але дозволяє запустити (юзер може свідомо сканувати без підказок карт, якщо `card_module_mode != "full"`).

### 9.6. Lazy Monthly Reset (Скидання місячних лімітів)

**Проблема з cron-підходом:**
Cron-задача "скинути всі картки 1-го числа о 00:00" — це зайва інфраструктура (окремий scheduled job), яку треба підтримувати, і яка може впасти без алерту.

**Рішення — Lazy Reset:**
Місячні ліміти скидаються не за розкладом, а **при першому зверненні до картки в новому місяці**. Перевірка дешева — порівняння двох чисел.

**Реалізація:**
Додати поле `last_monthly_reset` (Timestamp) в `current_state`:

```python
def ensure_monthly_reset(card):
    now = datetime.now()
    last_reset = card.current_state.last_monthly_reset

    if last_reset.month != now.month or last_reset.year != now.year:
        # Перший запит цього місяця — скидаємо
        card.current_state.used_monthly_out = 0
        card.current_state.used_monthly_in = 0
        card.current_state.last_monthly_reset = now
        # Також скидаємо monthly notification flags
        card.current_state.notification_flags.notified_80pct_monthly_out = False
        card.current_state.notification_flags.notified_95pct_monthly_out = False
        db.update_card(card)
```

Ця функція викликається на початку кожного запиту до картки в Matching Engine та при будь-якій команді бота, що читає стан картки.

**Нове поле в `current_state`:**
```json
"last_monthly_reset": "2025-04-01T00:00:00Z"
```

**Чому lazy краще cron тут:**
- Якщо картка не використовувалась місяць — не треба торкати БД взагалі
- Скидання відбувається атомарно в рамках транзакції, що вже виконується
- Немає ризику race condition між cron і активним ордером
